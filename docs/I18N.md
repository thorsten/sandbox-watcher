# Localisation plan: English and German

Status: done, 2026-11-02; Steps 0 to 5 implemented and checked in the running app
on the Mac. Step 6 (translated command errors) is optional. Target release: 0.9.0.

The app is English only today. This plan makes it bilingual (English,
German) in a way that lets a third language be added by writing one
dictionary file per side. Every step has acceptance criteria; the order is
the suggested implementation order.

## 1. Where the text is

| Place                                      | Files                                                                        | Approx. strings | Handled in                                              |
| ------------------------------------------ | ---------------------------------------------------------------------------- | --------------- | ------------------------------------------------------- |
| Webview: components and `App.tsx`          | `src/App.tsx`, `src/components/*.tsx` (22 files)                             | ~300            | Step 2                                                  |
| Webview: pure helpers that build text      | `format.ts`, `usageFormat.ts`, `updateFormat.ts`, `actions.ts`, `network.ts` | ~30             | Step 1                                                  |
| Webview: labels in `types.ts`              | `RUNTIME_LABELS`, `AGENT_LABELS`                                             | product names   | stay as is                                              |
| Shell: tray menu and tooltip               | `src-tauri/src/tray.rs`                                                      | ~8              | Step 3                                                  |
| Core: OS notifications                     | `crates/sandbox-core/src/notify.rs`                                          | ~18             | Step 3                                                  |
| Core: command errors (`Result<_, String>`) | `actions.rs`, `allowlist*.rs`, `diagnostics.rs`, `src-tauri/src/lib.rs`      | ~40             | Step 6, optional                                        |
| Core: diagnostics plain text               | `diagnostics::render_text`                                                   | —               | stays English: it is pasted into GitHub issues          |
| Website                                    | `site/`                                                                      | —               | out of scope; imprint and privacy are already bilingual |

Not translated, by design: container names, commands (`sandbox run claude`),
log lines, config lines shown by the Allow dialog, model ids, runtime and
agent product names, and anything Docker or ssh reports.

## 2. Decisions (to be recorded as ADR 0003)

1. **Language is a setting with a system default.** `Settings.language`
   gets the values `system | en | de` (serde default `system`, kebab-case
   like every other enum). The Settings panel shows a "Language" select
   next to "Theme". A change applies immediately, no restart.
2. **The Rust side resolves the effective language.** The pure resolver
   `i18n::Language::resolve(choice, system_locale)` lives in core with its
   tests, `en` as fallback; the shell reads the system locale with the
   `sys-locale` crate (no dependencies on desktop) in `Watcher::language()`.
   The webview asks the shell (`resolved_language` command, re-read after
   every settings save) instead of reading `navigator.language`. Reason: in a
   WKWebView `navigator.language` follows the app bundle's declared
   localisations, not the user's system language, so the two sides would
   disagree. One resolver on the Rust side keeps tray, notifications and UI
   in the same language. This also matches the rule that decisions live in
   Rust.
3. **No i18n library in the webview.** A typed dictionary:
   `src/i18n/en.ts` is the source of truth (`as const` object), `de.ts` is
   declared as `typeof en`, so a missing or extra German key fails `tsc`.
   `src/i18n/index.tsx` provides a module-level `t()`/`tx()` (the latter
   for sentences wrapping a `<code>`), `setLanguage()` (same pattern as
   `applyConfirmStop` in `actions.ts`) and a `LanguageProvider` that sets it
   for a tree. Components call `t` directly: App re-renders the whole tree
   on a change, and some tests call components as plain functions, so no
   hook is involved; a memoised component would read `useLanguage()`. Plurals use `Intl.PluralRules`, with
   `{ one, other }` forms per key. Dates and numbers use `Intl.DateTimeFormat`
   and `Intl.NumberFormat` with the resolved language. ~330 strings do not
   justify `react-i18next` (two runtime dependencies, JSON files without
   compile-time completeness). Revisit if ICU features such as gender or
   select are ever needed.
4. **No i18n crate on the Rust side either.** `crates/sandbox-core/src/i18n.rs`
   holds `enum Language { En, De }` and one function per text with an
   exhaustive `match`, so a new language variant does not compile until
   every text has it. ~26 strings.
5. **German addresses the user as "du"** (developer tool, informal;
   confirmed by the maintainer on 2026-11-02). Glossary (confirmed the same
   day):

   | English            | German                                 |
   | ------------------ | -------------------------------------- |
   | sandbox, container | Sandbox, Container (unchanged)         |
   | session            | Session (unchanged; plural "Sessions") |
   | turn               | Turn (unchanged; plural "Turns")       |
   | prompt             | Prompt (unchanged; plural "Prompts")   |
   | host, remote host  | Host, Remote-Host                      |
   | allow list         | Allow-Liste                            |
   | blocked request    | blockierte Verbindung                  |
   | stale (container)  | veraltet                               |
   | mount              | Mount                                  |
   | tray               | Menüleiste (macOS) / Taskleiste        |
   | Stop all           | Alle stoppen                           |
   | This machine/Mac   | Dieser Rechner / Dieser Mac            |

## 3. Steps

### Step 0: Setting and plumbing (half a day)

- `LanguageChoice` and `Settings.language` in `settings.rs`;
  `Language::resolve` in `i18n.rs` with a unit test for each of `system`,
  `en`, `de` and an unknown system locale.
- `sys-locale` added to the shell; `cargo deny check` passes.
- Command `resolved_language` in `src-tauri/src/lib.rs`. `save_settings`
  already pokes the watcher, whose refresh calls `tray::update`, so menu
  labels switch at once once Step 3 translates them.
- `src/types.ts`: `Language` type and `Settings.language`; contract fixtures
  regenerated (`SANDBOX_WATCHER_UPDATE_CONTRACTS=1`), `pnpm check:contracts`
  passes.
- Settings panel: "Language" select (System, English, Deutsch). Labels of the
  select itself are shown in their own language.

Acceptance: switching the setting changes `document.documentElement.lang`
and the webview re-renders; mock mode (`pnpm tauri:dev:mock`) works.

### Step 1: Webview infrastructure and pure helpers (one day)

- `src/i18n/en.ts`, `de.ts`, `index.tsx` as decided above. Keys are
  namespaced by component (`sidebar.noContainers`, `settings.language`).
- Interpolation `t("x", { n: 3 })`; plural keys as
  `{ one: "{n} session", other: "{n} sessions" }` picked through
  `Intl.PluralRules`.
- `index.html` keeps `lang="en"`; the provider sets `documentElement.lang`.
- Migrate the pure helpers: `formatUptime`, `formatRelative`,
  `formatDuration`, `formatCost` (currency through `Intl.NumberFormat`,
  `≈` prefix kept), `formatTokens` (locale decimal separator),
  `describeInterruption*`, `describeStopReport`, `updateFormat.ts`. Replace
  the three `toLocaleString()`/`toLocaleTimeString()` calls with a shared
  `formatDateTime(iso)` that uses the resolved language.
- Tests: existing helper tests run in `en` (the default); add one `de`
  case per helper. Add `src/i18n/i18n.test.ts`: plural forms, missing
  parameter, fallback to `en` for an unknown language.

Acceptance: `pnpm lint && pnpm format:check && pnpm test && pnpm build`
pass; no component changed yet.

### Step 2: Migrate the components (two to three days)

Batches, each one commit, German texts generated with the keys (glossary
and "du" form from section 2, reviewed in the app in Step 4):

1. Shell: `App.tsx`, `Sidebar`, `RuntimeBanner`, `UpdateBanner`,
   `StopAllButton`, `ConfirmDialog`, `ContainerActions`.
2. Detail: `DetailPane`, `ActivityPanel`, `FilesList`, `TurnsSection`,
   `NetworkPanel`, `ResourcesPanel`, `LogsPanel`, `MountsPanel`, `AllowDialog`.
3. Settings: `SettingsPanel`, `RemoteHostsSection`, `DiagnosticsSection`,
   `DockerContextsList`.
4. `HistoryView`.

Rules while migrating: `aria-label`, `title` and `placeholder` attributes
count as text; `<code>` content and commands stay literal; sentences are
one key each, never assembled from fragments (German word order differs).
`Sparkline` has no text.

Tests: the existing render tests keep asserting English and stay green.
Per batch add one German render test for the component with the most text
(`Sidebar`, `DetailPane`, `SettingsPanel`, `HistoryView`) wrapped in
`LanguageProvider language="de"`, plus a guard test that renders every
component once in `de` with the fixtures and fails on a short list of
English phrases that are easy to leave behind ("Stop", "Settings",
"session", "ago"). `src/test/render.tsx` and `dom.tsx` get a `language`
option, default `en`.

Acceptance: `grep` for JSX text literals and quoted sentences in
`src/components` and `App.tsx` finds only product names, commands and
code; `pnpm tauri:dev:mock` in German shows no English on any tab, the
Settings panel, the confirmation dialog and the Allow dialog.

### Step 3: Tray and notifications (half a day)

- `tray.rs`: menu labels, "No running sandboxes", the per-project label with
  its plurals ("3 Sessions"), tooltip. `build_menu` takes `Language`.
- `notify.rs`: titles and bodies through `i18n.rs`; `diff` takes `Language`.
  Existing tests pass `Language::En`; one test per notification kind in
  German.
- Language change at runtime: `save_settings` already triggers the tray
  rebuild from Step 0; notifications read the language when they are built.

Acceptance: tray menu and a session-started notification appear in German
on macOS; Windows and Linux tray checked in CI's app job at least for
compile and in a manual run.

### Step 4: Visual and length check (half a day)

German runs 20 to 30 percent longer. Check the sidebar cards, the tab
strip, Settings labels, the confirmation dialog buttons and the tray menu
on macOS at the default window size. Widen or wrap where needed in
`styles.css`; no per-language CSS. Screenshots of both languages for the
release notes and the README.

### Step 5: Documentation and release (half a day)

- ADR 0003 with the decisions of section 2.
- `AGENTS.md`: a rule under "Rules that matter": every user-visible string
  goes through `t()` with a key in `en.ts` and `de.ts`; tray and
  notification texts through `i18n.rs`; `types.ts` label tables are product
  names, not text. Adding a language: one `xx.ts` typed as `typeof en`, one
  enum variant, one option in the select, nothing else.
- `README.md`: a Languages line; `docs/MILESTONES.md` backlog entry marked
  shipped; `docs/CHECKS.md`: the `de` guard test.
- Conventional Commit `feat(ui): german translation` or per batch, then
  `pnpm release` for 0.9.0.

### Step 6, optional later: translated command errors

Errors from Tauri commands are `String`s today and are shown as they are.
If they should be German too: a `UserError { code, params }` type in core
serialised kebab-case, translated in the webview, and `code` listed in the
contract fixtures like every other enum. Technical causes (Docker, ssh)
stay as untranslated detail. Decide after Step 5 whether this is worth
touching ~40 call sites; the plain English is acceptable for 0.9.0.

## 4. Risks

- **Divergent language between UI and tray.** Mitigated by the single Rust
  resolver (decision 2). Test: change the setting, both switch.
- **Tests coupled to English text.** Existing tests keep `en` as default,
  so the migration does not rewrite ~190 assertions. German coverage is
  added, not substituted.
- **Forgotten strings.** `typeof en` catches missing German keys; the `de`
  guard test and the grep in Step 2 catch strings that never got a key.
- **Pluralisation shortcuts** like `session${n === 1 ? "" : "s"}` in
  `actions.ts`, `tray.rs` and the components must all become plural keys;
  German "1 Container, 2 Container" has no suffix and tests should cover
  the `one` and `other` forms of each.
- **Number and currency formats.** German decimal comma in costs and token
  counts is correct but changes existing test expectations; keep the
  English tests and add German ones rather than switching defaults.

## 5. Effort

About five to six working days for one person, Steps 0 to 5. The German
texts are generated together with the keys in Step 2, following the
glossary and the "du" form of section 2; the maintainer reviews them in
the running app during Step 4 rather than writing them up front.
